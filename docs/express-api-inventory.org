* About this document
This is the verified inventory of the JavaScript surface that express-cljs wraps: Express
5 (HTTP application, router, request, response, built-in middleware, server lifecycle) and
the =ws= package (WebSocket server on the same HTTP server), plus the design space of the
RPC layer that mounts one method registry over both transports. It is research only;
implementation happens in later phases (section 12 is the Phase 2/3/4 outline).

*Product constraint that shapes everything below:* the finished library is
ClojureScript-only at every call site: no =^js= hints, no JS interop outside ONE binding
namespace (=express-cljs.core=), kebab-case keyword maps in and out, promesa promises for
every async operation, core.async channels for websocket messages and lifecycle events,
and zero runtime npm dependencies beyond =express= and =ws=. Handlers are functions of a
request *map* returning a response *map* (or a promise of one); =req= / =res= / socket
objects never reach user code. Every upstream fact below is therefore paired with the
consequence for that design (sections 11 and 12).

** 1.3 Router lineage [README router][README path-to-regexp][SRC express/lib/express.js]
- Express 5 no longer contains its own router: =express.Router= *is* the =router@2.2.0=
  package (=exports.Router = Router=, =exports.Route = Router.Route=), which wraps
  =path-to-regexp@8=. =router= "can be used with a plain =http.createServer=" and adds
  only =next('router')= / =next('route')= semantics on top.
- =router(options)=: =strict= (default =false=: trailing slashes optional),
  =caseSensitive= (default =false=), =mergeParams= (default =false=). [DTS RouterOptions]
  lists the same three keys.
- Handlers "can optionally return a Promise… if the promise is rejected, =next= will be
  called with the rejected value, or an error if the value is falsy" — this is the whole
  async contract; a *resolved* promise is ignored (the handler must still respond).
- Error-handling middleware = arity-4 functions =(err, req, res, next)=; "as long as the
  error is in the pipeline, normal middleware and handlers will be bypassed".
- =router.param(name, fn)= positions the middleware "in the same stack as =.use=" and also
  honours a returned promise (LIVE: an async param handler that throws → 500 through the
  error chain).
- =express= 5 exports exactly: =Route Router application json raw request response static
  text urlencoded= [LIVE =Object.keys(express)=]. There is no =express.query= (4.x had it)
  and no =express.Router().ws= (=typeof= is ="undefined"= until express-ws monkeypatches it).

** 1.4 Async handler semantics — what 5.2.1 actually does [LIVE]
| Handler behaviour | Observed response (=NODE_ENV= unset, no error middleware) |
|-------------------+----------------------------------------------------------|
| =async= handler throws =Error('boom-async')= | 500, HTML body with the *stack trace*, =console.error= of the stack |
| synchronous throw | identical to the rejection path (500 + stack) |
| rejects with a *string* =throw 'string-reason'= | 500, body =<pre>string-reason</pre>= (the string is used as the message) |
| rejects with =undefined= | 500, =Error: Rejected promise= synthesised by =router/lib/layer.js:161= |
| rejects with =err.status = 418= and =err.headers = {'x-tea': 'yes'}= | *418*, header =x-tea: yes= sent, stack body |
| rejects with =err.status = 500, err.expose = false= | 500, stack body — =expose= is *not* consulted by finalhandler (section 8.1) |
| =next(new Error('via-next'))= | same as a rejection |
| error thrown inside an arity-4 error middleware | forwarded to the next error handler / finalhandler (500 =second-from-error-mw=) |
| =NODE_ENV=production= | body is only the reason phrase (=Internal Server Error=, =Unprocessable Entity=, =Too Many Requests=, =Bad Request=), never the message, even for exposed 4xx errors |
Conclusion: Express 5 gives the wrapper a reliable "rejection → error chain" guarantee,
but its *default renderer* is HTML-only and message-less in production, so the wrapper
installs its own final error middleware (section 8.5) and content-negotiates JSON.

** 1.5 Recommendation
*Express 5.2.1.* Evidence: it is =latest= on npm; it is the only line receiving features
(5.1.0 =Uint8Array= bodies, =ETag= option on =sendFile=; unreleased master already carries
the body-parser 2.3.0 fail-open fix CVE-2026-12590, which our install has); it needs Node
≥ 18 which we exceed (22.23.2); the native promise forwarding removes an entire class of
"forgot =.catch(next)=" bugs that a promesa-based wrapper would otherwise have to re-create;
the router is a standalone package with a documented semantics; the path-to-regexp 8
syntax is stricter (throws on ambiguity, no ReDoS-prone regex-in-string) which suits a
routing-as-data design. 4.22.3 is maintenance-only and its =0.1.x= path-to-regexp accepts
regexes in strings that we would have to police ourselves. Nothing the RPC or WebSocket
layers need exists only in 4.x.

** 2.2 How express-ws works and why it is brittle [SRC express-ws/lib/index.js, add-ws-method.js, websocket-url.js, wrap-middleware.js]
1. =expressWs(app, server?, {leaveRouterUntouched, wsOptions})= creates =http.createServer(app)=
   when no server is passed and *replaces =app.listen=* with =server.listen=.
2. It monkeypatches =app.ws= and — unless =leaveRouterUntouched= — the *global*
   =express.Router= prototype with a =.ws(path, ...handlers)= method.
3. =.ws(path, h)= registers a fake *GET* route at =path + '/.websocket'= (query preserved)
   whose middleware unwraps =req.ws= and calls =h(ws, req, next)=; non-websocket requests
   to that fake route call =next()=.
4. It creates =new ws.Server({server})= (ws 7) so *every* =upgrade= on the HTTP server is
   accepted by it; on ='connection'= it rewrites =request.url= to the =/.websocket= form,
   builds a dummy =http.ServerResponse= whose =writeHead(status > 200)= closes the socket,
   and runs =app.handle(request, dummyResponse, cb)=; if no =.ws= route marked the request
   handled, the socket is closed.
Consequences: (a) it owns the upgrade event, so no second =WebSocketServer= (or our own
upgrade auth) can coexist; (b) it depends on Express internals (=app.handle=, the Router
factory-is-prototype hack the source itself calls "Here be dragons"); (c) ws 7 lacks 8.x
fixes and API (=allowSynchronousEvents=, =autoPong=, =wsClientError=, =closeTimeout=,
=maxBufferedChunks=, =maxFragments=); (d) the handshake is already *complete* when Express
middleware runs, so an auth failure can only =socket.close()= after a 101, never answer
401/403; (e) it is unmaintained since 2021 in practice.

** 2.3 Plain ws on the HTTP server (=noServer= + =upgrade=) [DOC ws README "Multiple servers sharing a single HTTP/S server", "Client authentication"][DOC node http 'upgrade'][LIVE]
- Create =new WebSocketServer({noServer: true, ...})= and listen to the HTTP server's
  ='upgrade'= event yourself; route on =request.url= pathname; for accepted paths call
  =wss.handleUpgrade(req, socket, head, ws => wss.emit('connection', ws, req))=; for the
  rest write a raw HTTP response (=HTTP/1.1 404 Not Found\r\n\r\n=) and =socket.destroy()=.
- Node: "By default all HTTP upgrade requests are ignored … unless you listen to this
  event, in which case they are all accepted" — so the wrapper must always answer
  non-matching upgrades itself. Node 22.21+ adds a =shouldUpgradeCallback= server option
  for finer control (not needed).
- Authentication happens *before* =handleUpgrade= with the full HTTP request (headers,
  cookies, query) and can answer 401/403 as a proper HTTP response; the ws docs explicitly
  discourage =verifyClient= in favour of this.
- LIVE: an upgrade to a non-websocket path answered with a hand-written 404 produced a
  client-side ='unexpected-response'= event with =statusCode 404=; the accepted path
  delivered the upgrade request (=url=, =sec-websocket-protocol=, =cookie=, custom =x-auth=
  header, =socket.remoteAddress=) to the ='connection'= listener.
- The same HTTP server keeps serving Express for normal requests; no monkeypatching.

** 2.4 Recommendation
*Plain =ws= 8.21.3 in =noServer= mode on the wrapper-created =http.Server=; express-ws is
rejected.* Evidence: 2.1 (maintenance and the ws 7 pin), 2.2 (mechanics), 2.3 (the official
pattern gives everything express-ws gives — path routing, access to the upgrade request,
sharing one server — plus pre-handshake auth and Node-native close choreography, section
5.7). "Both" is not needed: the wrapper's =ws/serve!= takes a path (or a predicate) and
the rest of the upgrade traffic is answered 404. The dev dependency set is therefore
=express= + =ws= (+ =@types/*= for the census only; they are not required at runtime).

** 3.3 Ordering, precedence and flow control [README router][LIVE]
- Layers run in *registration order*; the first matching route whose handler responds
  wins. There is no specificity sort: register =/users/me= before =/users/:id=.
- =next()= continues to the next matching layer; =next('route')= skips the remaining
  handlers of the *current route* and continues with the next route (LIVE: =/chain= first
  route set =x-first: 1= then =next('route')=, second route answered =second-route= and the
  header survived); =next('router')= exits the current =Router= to its parent.
- =next(err)= (or a rejection) switches the pipeline to *error middleware only* (arity 4)
  until one responds; if none does, =finalhandler= renders it (8.1).
- A handler that neither responds nor calls =next= leaves the request pending forever
  (router README: "the request will stall if this is not called"). The wrapper's adapter
  always ends the request: a response map → response; =nil= → =next()= (explicit
  fall-through, section 11.4); a rejection → =next(err)=.
- *Implemented (Phase 3):* =next('route')= / =next('router')= are exposed as return-value
  sentinels, not as a =next= argument: a handler returns =(route/next-route)= or
  =(route/next-router)=; =(route/continue {:user u} {:x-request-id id})= is =next()= plus
  keys merged into every later request map (the replacement for mutating =req=) plus
  response headers set immediately. =route/control?= recognises the three.
- Automatic behaviour without user routes: =HEAD= is served by the =GET= route (LIVE
  =HEAD /plain= → 200, headers of the GET, empty body); =OPTIONS= on a routed path answers

** 4.3 Error middleware and chains [README router][DTS ErrorRequestHandler, NextFunction][LIVE]
- Arity decides the kind: 4 parameters =(err, req, res, next)= = error middleware; ≤ 3 =
  normal. =[DTS NextFunction]= documents =next()=, =next(err)=, =next('route')=,
  =next('router')=.
- Error middleware runs *only* while an error is in the pipeline, in registration order;
  it may respond, call =next(err)= to pass on, or =next()= to resume normal flow.
- Async rejection semantics: section 1.4 (all handler kinds, including =param= handlers
  and error middleware, get their rejections forwarded).
- LIVE: an arity-4 handler mounted with =app.use('/handled', ...)= received the error and
  answered 599 JSON; a throw inside error middleware went to the next handler.
- Wrapper adapter (11.4): user handlers are =(fn [req-map] -> response-map | promise)=
  and *never* see =next=; the adapter decides =next()= vs response vs =next(err)=; the
  wrapper's final error middleware (8.5) is registered last by =core/app= and is the only
  arity-4 function in the stack unless the user adds =:error-handler=.

** 4.4 =finalhandler= 2.1.1 — the Express 5 default handler [README finalhandler][SRC finalhandler/index.js][LIVE]
- Invoked with no error → 404 HTML =Cannot <METHOD> <path>=; with an error → status from
  =err.status= / =err.statusCode= when 4xx–5xx else 500, =res.statusMessage= from the
  code, headers from =err.headers= (copied), body = =err.stack= (or =err.toString()=) when
  =env !== 'production'= else the status phrase; adds =Content-Security-Policy:
  default-src 'none'= and =X-Content-Type-Options: nosniff=; unpipes =req=; when headers
  were already sent it destroys the socket instead. =err.expose= is *never* read.
- =env= comes from the app's ='env'= setting (=app.handle= passes it) and =onerror= logs
  the stack with =console.error= unless =env === 'test'=.
- LIVE: development bodies contain full stacks (an information leak); production bodies
  hide even exposed 4xx messages; the =Content-Type= is always =text/html= regardless of
  =Accept: application/json=. Hence the wrapper's own final middleware (8.5).

|----------+-------------------------+-------|
| A: =server.close()= alone | *never* (1.5 s timeout) | Node ≥ 19 closes *idle HTTP* keep-alive connections inside =close()= (it did: the idle agent socket did not block), but upgraded ws sockets are neither idle-HTTP nor tracked |

House choreography (Phase 3 =core/close!=): (1) stop accepting: =server.close(cb)= (also
reaps idle keep-alive connections on Node ≥ 19); (2) for every tracked ws client send

(default 5000) call =server.closeAllConnections()= for stuck HTTP requests; (5) resolve

anyway, 6.7). Result: the process exits by itself — LIVE the final probe reported only
=PipeWrap= (stdio) and the unref'd =Timeout= as active resources. =process.on('SIGTERM')=

** 6.7 Keepalive (ping/pong) and the unref precedent [README ws "How to detect and close broken connections"][DOC email-cljs parse-binding]
- ws does *not* detect dead peers by itself; the README pattern: mark =isAlive=false=,
  =ping()= every 30 s from one =setInterval= over =wss.clients=, =terminate()= sockets that
  did not =pong= since the previous tick; clear the interval on =wss.close=.
- House rule (email-cljs precedent: =parse-binding/set-timer= unref's every watcher
  timer so an idle process exits on its own): the keepalive interval is created in the
  binding with =timer.unref()= (LIVE sanity: an unref'd interval leaves only =Timeout= in
  =process.getActiveResourcesInfo()= and does not keep the process alive). Wrapper
  options: =:keepalive-ms= (default 30000, =false= disables), =:keepalive-grace-ms=
  (default = interval), closes with =terminate()= (README recommends terminate over
  close for dead peers).
- Clients receive automatic pongs (=autoPong=), so the client side needs no code.

** 6.8 Backpressure [DOC ws.md bufferedAmount, pause/resume][README]
- =bufferedAmount= grows when the socket cannot flush; the wrapper's =send!= returns a
  promise resolved on the write callback and =ws/buffered-amount= exposes the counter;
  =:max-buffered-bytes= (default 8 MiB) makes =send!= reject with
  =:express-cljs/ws-error {:code :backpressure}= instead of buffering unboundedly.
- Receive side: the per-connection core.async channel has a fixed buffer
  (=:message-buffer= default 64); when it is full the binding calls =ws.pause()= and
  =resume()=s once the consumer drains below half (=put-or-cancel!= from the leveldb
  precedent handles the consumer-closed case).

** 6.9 Subprotocols and upgrade headers
- Client offers =Sec-WebSocket-Protocol: a, b=; without =handleProtocols= ws selects the
  first (LIVE); with it, the function receives a =Set= and the request and returns one
  name or =false= (header omitted). If the client offered protocols and the server
  selects none, browsers fail the connection — the wrapper's =:protocols= list therefore
  answers =false= only when nothing matches, and the RPC layer registers ="express-cljs-rpc"=
  (7.1) as an optional protocol name.
- Any request header is readable on the upgrade request; cookies and =Authorization=
  are the common auth carriers; the wrapper's =:authenticate (fn [upgrade-map] ->
  ctx | promise | nil)= runs *before* =handleUpgrade= and answers 401 on =nil= / 403 on a
  thrown =http-error=.

  ={room #{conn-id}}= kept by =express-cljs.ws=; a connection leaving (close event)

* 7. RPC layer design space (pre-decision for Phase 4)
** 7.1 Frame shape over ws: JSON-RPC 2.0 vs a home-grown ={method params id}= [DOC jsonrpc.org/specification]
| Criterion | JSON-RPC 2.0 | Home-grown |
|-----------+--------------+------------|
| interop | any existing client library / MCP-style tooling speaks it; error codes standardised | none |
| envelope | =jsonrpc:"2.0"= + =method= + =params= (object *or* array) + =id= (string / number / null) → =result= xor =error {code message data}= | whatever we choose |
| notifications | request without =id=: server MUST NOT reply | must invent |
| batch | array of requests → array of responses; MUST NOT reply to notifications inside | must invent |
| cost | one extra key per frame; strict =id= rules | none |
*Recommendation: JSON-RPC 2.0, single-request only (no batch), with notifications.*
Frames are UTF-8 *text* frames carrying one JSON document. Batch arrays are answered
with =-32600 Invalid Request= (=data.reason = "batch not supported"=): batches add
ordering/partial-failure semantics for no benefit on a persistent socket (ws already
pipelines), and even the Model Context Protocol dropped them in 2025. Kept as a marker
(=:batch?= option, uncertainty 10.13) if a consumer needs it later.

** 7.2 HTTP transport: single =POST /rpc= vs per-method routes
*Recommendation: one endpoint (default =/rpc=, configurable), same JSON-RPC body,
=Content-Type: application/json=, response 200 with the JSON-RPC response object for
both results *and* method errors* (per spec the transport status is independent of the
RPC outcome); HTTP-level codes only for transport failures: 400 (parse / invalid request),
404 (endpoint), 405 (non-POST), 413 (body limit), 415 (wrong content type), 204 for a
notification (no =id=), 500 for a wrapper bug. Optional =:http-status-from-error? true=
maps method errors to the status column of =util/rpc-error-codes= for REST-ish clients
(the body stays a JSON-RPC error object). Per-method routes are not generated: they
would duplicate the registry, fight the router's method semantics and lose the
notification/id model.

** 7.3 Shared registry
={"name" (fn [params ctx]) …}= built by =rpc/registry= (validates names are non-empty
strings, allows a =:schema= per method for later); the *same* registry value is passed to
=rpc/http-routes= and =rpc/serve-ws!=; dispatch (=rpc/call!=) is one pure-ish function
=(registry frame ctx) -> promise of response frame | nil (notification)= so the two
transports differ only in framing and context. Method fns may return a value or a
promise; a thrown / rejected =util/rpc-error= becomes the error object; any other error
becomes =-32603 Internal error= with the message hidden unless =:expose-errors? true=.
Reserved names: anything starting with =rpc.= (spec), plus the wrapper's built-ins
=rpc.ping= (health), =rpc.methods= (introspection, opt-in).

** 7.4 Error mapping (=util/rpc-error-codes=, Phase 0)
| Wrapper code | JSON-RPC code | HTTP status (opt-in mapping) | ws |
|--------------+---------------+------------------------------+----|
| =:parse-error= | -32700 | 400 | error frame with =id nil= |
| =:invalid-request= | -32600 | 400 | error frame with =id nil= (or the given id when parseable) |
| =:method-not-found= | -32601 | 404 | error frame |
| =:invalid-params= | -32602 | 400 | error frame |
| =:internal-error= | -32603 | 500 | error frame |
| =:unauthorized= / =:forbidden= | -32001 / -32002 (implementation range -32000..-32099) | 401 / 403 | error frame; a *transport-level* auth failure closes with 3000 (=rpc-unauthorized=) |
| =:timeout= | -32003 | 504 | error frame |
| =:application= | -32000 (+ =data= from the method) | 500 | error frame |
ws close codes reserved by the RPC layer: 3000 unauthorized, 3001 protocol violation
(non-JSON frames after =:strict?=), 3002 server overloaded.

** 7.5 Request-id correlation, notifications
- Server responses echo the client's =id= verbatim (string or number); =null= ids are
  only produced for parse / invalid-request errors (spec). Client-side helper
  =rpc/client= (Phase 4, ws only) keeps ={id promise}= and rejects all pending on close.
- A frame without =id= is a notification: dispatched, never answered (HTTP → 204).
- Server → client frames without =id= are *server notifications* (=rpc/notify! conn
  "events/tick" params=), the JSON-RPC-native push mechanism (LSP / MCP style).

** 7.6 Streaming results — in scope as notifications, not as a result stream
A method that wants to stream calls =(notify! "jobs/progress" {:id id …})= from its
=ctx= (ws only; on HTTP =notify!= is =nil= and the method should check =:transport=)
and finally returns the result. Correlation is the request =id= inside =params= by
convention (=:id= from ctx). A subscription API (=rpc.subscribe= built-in + rooms) is
=later= (10.14); the primitive exists.

** 7.7 Auth context injection
- HTTP: =rpc/http-routes … {:context (fn [req-map] -> map | promise)}=; the fn sees the
  translated request (headers, cookies, =:ip=) and returns the ctx merged with
  ={:transport :http :request req-map}=; throwing =http-error= answers at HTTP level.
- ws: =ws/serve! … {:authenticate (fn [upgrade-map])}= decides the handshake; the value it
  returns is the *connection ctx* stored with the connection and merged into every call's
  ctx as ={:transport :ws :conn conn :notify! f :id id}=.

** 7.8 Proposed syntax (verbatim proposal for Phase 2–4; docstrings win once written)
#+begin_src clojure
(require '[express-cljs.core :as core]
         '[express-cljs.route :as route]
         '[express-cljs.middleware :as mw]
         '[express-cljs.ws :as ws]
         '[express-cljs.rpc :as rpc]
         '[promesa.core :as p]
         '[cljs.core.async :as async :refer [<! go-loop]])

;; --- HTTP: handlers are (fn [req] -> response-map | promise | nil = fall through) ---
(def routes
  (route/routes
    (route/get  "/health"        (fn [_] {:status 200 :body {:ok true}}))
    (route/get  "/users/:id"     (fn [{:keys [params]}]
                                   (p/let [u (db/user! (:id params))]
                                     (if u {:body u} (throw (core/http-error 404 "no such user"))))))
    (route/post "/users"         [(mw/json {:limit "1mb"})]           ; per-route middleware vector
                                 (fn [{:keys [body]}] {:status 201 :body (db/create! body)}))
    (route/get  "/files/*splat"  (fn [{:keys [params]}] {:send-file {:path (str/join "/" (:splat params))
                                                                   :root "/srv/files"}}))
    (route/router "/admin" {:merge-params? true}                     ; sub-router
      (route/use  [(mw/basic-auth {:realm "admin" :check (fn [user pass] ...)})])
      (route/get  "/" (fn [_] {:body "admin"})))
    (route/static "/static" "/srv/public" {:dotfiles :ignore :max-age "1d"})))

;; --- RPC: one registry, two transports ---
(def methods
  (rpc/registry
    {"math/add"  (fn [{:keys [a b]} _ctx] (+ a b))
     "users/get" (fn [{:keys [id]} {:keys [auth]}]
                   (when-not auth (throw (rpc/error :unauthorized "login first")))
                   (db/user! id))                                    ; promise ok
     "jobs/run"  (fn [params {:keys [notify! id transport]}]
                   (p/do (when notify! (notify! "jobs/progress" {:id id :pct 50}))
                         (run-job! params)
                         {:done true}))}))

(def app
  (core/app {:env :production :trust-proxy :loopback :x-powered-by? false
             :etag :weak :query-parser :simple
             :error-handler (fn [err req] nil)}                      ; nil = wrapper default rendering
    routes
    (rpc/http-routes methods {:path "/rpc"
                              :context (fn [req] {:auth (get-in req [:headers :authorization])})
                              :limit "256kb"})))

(p/let [server (core/listen! app {:port 8080 :host "127.0.0.1"
                                  :request-timeout-ms 120000 :keep-alive-timeout-ms 5000})
        wss    (ws/serve! server {:path "/ws" :max-payload 1048576 :keepalive-ms 30000
                                  :protocols ["express-cljs-rpc"]
                                  :authenticate (fn [{:keys [headers query]}]
                                                  (when-let [tok (:x-auth headers)]
                                                    {:auth (verify tok)}))})]
  ;; raw websocket use: one channel per connection, close = unsubscribe
  (go-loop []
    (when-let [{:keys [conn] :as ev} (<! (ws/connections wss))]      ; {:event :open :conn ..}
      (go-loop []
        (when-let [m (<! (ws/messages conn))]                        ; {:type :text :data "..."} | {:type :binary :data buf}
          (ws/send! conn (str "echo " (:data m)))
          (recur)))
      (recur)))
  (ws/broadcast! wss {:json {:hello "all"}})
  (ws/join! wss conn "room:1") (ws/broadcast! wss "room:1" "hi room")
  ;; RPC over the same socket
  (rpc/serve-ws! wss methods {:context (fn [conn] (:auth (ws/ctx conn)))})
  ;; shutdown: server.close + ws 1001 choreography + deadline
  (core/close! server {:timeout-ms 5000 :ws-close-timeout-ms 2000}))

** 8.5 Wrapper mapping and rendering (implemented in =util= Phase 0; rendering Phase 2)
| Source | Wrapper ex-info | Rendered by =core/error-response= (final arity-4 middleware) |
|--------+-----------------+--------------------------------------------------------------|
| handler throws / rejects =util/http-error= | =:express-cljs/http-error {:status :message :expose? :headers :body}= | status; =:headers=; body ={:error {:status :message}}= as JSON when the client accepts JSON (or the request was JSON), else =text/plain= =<status> <message>=; message shown when =:expose?= (default =< 500=) else the reason phrase |
| handler throws anything else (ex-info with =:status=, JS Error, string) | classified by =util/error-status= | 500 (or the foreign status) with the reason phrase; message only when =:env= is not =:production= *and* =:expose-errors?= (default =true= outside production) |
| body-parser / serve-static / =res.format= http-errors | =:express-cljs/http-error= with =:reason= from =err.type= (4.1) and =:cause= | as above (they are 4xx → exposed) |
| no route | =core/not-found= | 404 ={:error {:status 404 :message "Not Found" :path ..}}= / text |
| =argument-error= raised inside a handler | 400 | exposed message |
| malformed response map (unknown key, two body keys, bad status) — =util/check-response!= | =:express-cljs/server-error {:code :invalid-response}= | 500 (*corrected from 11.4's "argument-error"*: a bad response map is a server bug, not a client error) |
| listen / close failures | =:express-cljs/server-error {:code :eaddrinuse …}= | promise rejection (never a response) |
| rpc | =:express-cljs/rpc-error= | JSON-RPC error object (7.4); on HTTP status 200 unless =:http-status-from-error?= |
Every rendering path also emits ={:event :error …}= on the server's core.async
=events= channel (11.5) instead of =console.error=, and the wrapper sets the app ='env'=
to =test= during its own tests to silence Express's logger.
** 8.6 Promise-rejection forwarding
The adapter wraps the user handler in =p/promise= + =p/catch= itself (viem =promised=
pattern), so *promesa* rejections, synchronous throws and non-Error rejection values all
reach =next(err)= as ex-info; Express's own forwarding (1.4) is a second net, never the
first. Falsy rejections become =:express-cljs/server-error {:code :rejected-falsy}=.

* 9. Pitfalls checklist for express-cljs (numbered)
1. *Route registration throws.* 4.x path syntax (=/*=, =:id?=, =(regex)=) throws
   =TypeError= at =app.get(...)= time with a =git.new/pathToRegexpError= link — surface it
   as an argument-error at =route/…= construction, before =core/app= runs.
2. *Wildcards are vectors and unmatched params vanish.* Never assume =(:ext params)= is
   present; =(:splat params)= is =["a" "b"]=.
3. *=/files/*splat= does not match =/files=.* Use =/files{/*splat}=.
4. *No 405 from Express.* Wrong method on a known path is a 404; use =route/resource=
   (=route(path).all=) when 405 matters.
5. *Handlers must respond or fall through.* A resolved promise without a response stalls
   the request; the adapter treats =nil= as =next()= and everything else as a response.
6. *Error bodies leak stacks in development and hide messages in production* — the
   wrapper owns error rendering (8.5). Never rely on =err.expose= with finalhandler.
7. *=extended= query/urlencoded parsing enables =allowPrototypes=* (Express's choice) and
   nests up to depth 32 (body) / 5 (query, qs default); keep =:simple= unless needed and
   validate bodies.
8. *Body parsers are silent on a wrong =Content-Type=* — =:body nil= is not an error; JSON
   with a non-Unicode charset is a 415; =limit= defaults to 100 kb (expose =:limit=,
   invalid strings now throw at startup).
9. *=req.is= returns =null= (not =false=) when there is no body.* Treat =nil= as "no body".
10. *ws =maxPayload= defaults to 100 MiB* — a single frame can allocate that much; the
    wrapper defaults to 1 MiB and the RPC layer to 256 kb.
11. *Static: =dotfiles :deny= turns into a 404 through =fallthrough=*, hidden directories
    in the path are ignored (5.x), and a missing file with =fallthrough false= renders an
    =ENOENT= stack in development.
12. *=sendFile= needs an absolute path or =:root=* (synchronous =TypeError=); with =:root=
    traversal is a 403 — always pass =:root=.
13. *Keepalive timers keep Node alive* unless =unref='d (email precedent); ws's per-socket
    =closeTimeout= (30 s) also delays exit after =close()= if the peer never answers —
    =terminate()= on the wrapper's own deadline.
14. *Trust proxy spoofing.* =:trust-proxy true= trusts every =X-Forwarded-*= header; use a
    subnet/name (=:loopback=, ="10.0.0.0/8"=) or a hop count; =X-Powered-By= is on by
    default in Express (wrapper default off).
15. *Multipart is out of scope* (=:body nil=); mount multer yourself via =mount-upstream!=.
16. *Signed cookies need =req.secret=* which only cookie-parser sets (LIVE throw) —
    uncertainty 10.3.
17. *ETag defaults*: weak ETags on every =send= / =json= (setting =:etag=), =serve-static=
    generates its own regardless; 304s appear automatically for conditional requests —
    tests must send fresh requests or disable =:etag=.
18. *404 handling has three levels* (3.7): finalhandler, static fallthrough, wrapper
    =not-found=; register the wrapper's last.
19. *Close choreography on Node 22*: =server.close()= waits forever with open websockets;
    =closeAllConnections()= skips upgraded sockets; =wss.close()= closes nothing —
    close/terminate every client (5.3).
20. *Every ws socket needs an ='error'= listener* or an emitted error crashes the process.
21. *ws ='message'= data is a =Buffer= even for text* — decode with =toString()= only when
    =isBinary= is false; a =Buffer= sent as-is is a binary frame.
22. *Close code validity*: 1004/1005/1006 and <1000 / 1015..2999 throw synchronously;
    reason strings > 123 bytes throw =RangeError=.
23. *=res.send= of a number/boolean is JSON* (not the 4.x status shortcut); the response
    map makes =:status= explicit so this cannot be confused.
24. *Header case*: Node lower-cases incoming names, keeps outgoing case as given; the
    wrapper normalises both directions to lower-case kebab keywords; =Set-Cookie= is the
    only multi-valued response header a client must read as a list.
25. *Sub-app settings inheritance* differs per setting (3.9); the wrapper uses routers,
    not sub-apps, by default.
26. *=npm audit= noise* comes from shadow-cljs, not express/ws; do not "fix" it with
    =--force= (that would jump to shadow-cljs 3.x).
27. *Node =fetch= turns conditional requests into reloads.* Any =If-None-Match= /
    =If-Modified-Since= header makes undici add =Cache-Control: no-cache= + =Pragma:
    no-cache=, so =fresh()= says stale and no 304 is produced. Send an explicit
    =Cache-Control= (e.g. =max-age=0=) from the client, or use =http.get= (Phase 2 finding).
28. *=p/let= awaits every promise binding.* Binding an in-flight request or a
    never-resolving deferred inside =p/let= blocks the whole form; bind such values with a
    plain =let= (two Phase 2 test hangs came from this).
29. *=mount-upstream!= appends after the routes.* Express runs layers in registration
    order and =core/app= registers its plan eagerly, so middleware that must run first
    (cors, helmet) goes in the route data as =(route/use (route/upstream f))=.
30. *Table-form routes are sorted by specificity, ordered-form routes are not.* A map
    has no source order; the table form sorts paths (literal < param < optional <
    wildcard, per segment; a strict prefix first; RegExps last), the ordered form
    (=route/routes=, vectors, tuples) is registered verbatim.
31. *promesa 12.0.1 poisons a microtask drain after a synchronous throw.* Its
    ClojureScript promise implementation (=promesa/impl/promise.js=, =processNextTick=)
    keeps a mutable local =state= across the tasks of one drain; a throwing =p/do= /
    =p/let= body (a =(throw (rpc-error ...))= in a method, an http-error in a handler)
    flips it to REJECTED for every later task queued on the same promise — and every
    =p/do= / =p/let= (and every =p/let= binding that evaluated to nil) queues on the
    shared =NULL_PROMISE= singleton. Those bodies never run and resolve with =nil=
    (a handler resolving nil is a silent =next()= → 404; an RPC notification is silently
    dropped). Found by the ws RPC tests, reproduced with three lines of promesa.
    House fix: =src/promesa/impl/promise.js= is a vendored copy re-reading the state per
    task (the source path shadows the jar); pinned by
    =util-test/promesa-drain-is-not-poisoned-by-a-throwing-body=. promesa 11.0.678 drains
    correctly but four existing tests fail on its other semantics, so no downgrade.
32. *A paused ws socket never emits ='close'=.* =ws.pause()= stops the receiver, and
    ws only emits =close= once the receiver finished draining; =terminate()= on a paused
    peer therefore resolves nothing on THAT side until it resumes. The wrapper's shutdown
    only awaits the server side (fine); tests resume before awaiting a client close.

* 10. Uncertain / needs verification (numbered; each with the recommended house position)
1. *Header key casing policy.* HTTP names are case-insensitive; Node lower-cases input.
   House position: lower-case kebab keywords (=:content-type=) in both directions,
   =util/->header-map= / =->wire-headers= (Phase 0, tested). Original spelling
   (=rawHeaders=) is not exposed.
2. *Client-side close code after a =maxPayload= violation.* The server-side =close= event
   showed 1006 (receiver error) and the source sends 1009 to the peer; the client-side
   code was not captured. Position: document "1009 expected, verify in the Phase 3
   tests" and make the wrapper's =ws-error= carry the =WS_ERR= code regardless.
   *SETTLED (Phase 4 tests + smoke): the client sees =1009= with an empty reason; the
   server-side close event stays =1006= and carries the ws-error
   ={:code :unsupported-message-length :close-code 1009}= under =:error=.*
3. *Signed cookies without cookie-parser.* =res.cookie(signed)= only needs =req.secret=;
   reading requires =cookie-signature.unsign= (HMAC-SHA256 base64, =s:= prefix) which is a
   transitive dependency we must not require. Position: Phase 2 implements sign/unsign
   with Node =crypto= inside the binding (=:cookie-secret= app option → =:signed-cookies=
   on the req map, =:signed? true= on cookie entries); verify byte-compatibility against
   =cookie-signature= in a test that requires it as a *dev* dependency only.
4. *=Set-Cookie= multiplicity through =fetch=.* The LIVE probe's =Headers.forEach= showed
   only the last cookie; this is a client artefact. Position: Phase 2 tests read
   =headers.getSetCookie()= (Node ≥ 19.7).
5. *=rawHeaders= / duplicate request headers.* Node joins duplicates with ", " except
   =set-cookie= (array) and =cookie= ("; "); =joinDuplicateHeaders= changes discarding
   rules for some headers. Position: not exposed; document.
6. *=:fresh?= / =:stale?= timing.* They depend on response headers; a lazily computed
   value inside the req map violates "plain map" purity. Position: expose
   =core/fresh?= taking the req map and the intended response headers instead of map
   keys; the map carries the raw conditional headers only. *Implemented as positioned*
   (=core/fresh?= / =core/stale?=, tested with a real 304 round-trip). Finding: Node's
   =fetch= appends =Cache-Control: no-cache= (and =Pragma=) to any request that carries
   a conditional header (Fetch spec cache-mode rule), which makes =fresh= — Express's and
   ours — report *stale*; a client that wants a 304 from =fetch= must send its own
   =Cache-Control= (pitfall 9.27).
7. *Trust-proxy value spelling.* Express accepts booleans, numbers, CSV strings, arrays,
   functions. Position: =:trust-proxy= accepts =true=/=false=, integer, keyword names
   (=:loopback= → "loopback"), a vector of strings/keywords, or a fn of =(ip index)=.
8. *Streaming responses / SSE.* =res.write= chunking is not in the response-map model.
   Position: =later=; =:body= may be a Node =Readable= (opaque, piped) in Phase 2 so SSE
   can be built on a =PassThrough= from the binding; a first-class =:stream= map is a
   Phase 5+ marker.
9. *Upgrade request =ip= / =protocol=.* The upgrade =IncomingMessage= is not an Express
   request, so =req.ip= does not exist there. Position: the wrapper derives =:ip=,
   =:ips=, =:protocol=, =:host= for the upgrade map with the *same* trust setting
   through =proxy-addr= semantics reimplemented in CLJS for the three named subnets +
   CIDR (small) — or, simpler, calls the Express request prototype getters by
   =Object.setPrototypeOf(upgradeReq, app.request)= inside the binding (what Express
   itself does in =app.handle=). Recommended: the prototype trick (zero reimplementation,
   verified pattern in =application.js=).
10. *=express-ws= compatibility with express 5 GA.* Only the alpha peer range is evidence;
    not tested here since it is rejected anyway (2.4).
11. *=res.jsonp=, =res.render=, views, MIME lookup, =app.engine=.* Position: =none= for v1
    (API server library); revisit if a consumer needs server-rendered HTML.
12. *=app.locals= / =res.locals=.* Position: not modelled; handler closures and the ctx
    map replace them; =res.locals= stays empty (Express initialises it).
13. *JSON-RPC batch.* Position: rejected with -32600 in Phase 4; =:batch?= option is a
    marker.
14. *RPC subscriptions / result streams.* Position: notifications + rooms primitives in
    Phase 3/4; a =rpc.subscribe= convention is =later=.
15. *=QUERY= method.* Present on Node 22 and therefore on Express; semantics (safe,
    cacheable) are still an IETF draft. Position: exposed as =route/query= when the
    binding reports it; no special casing.
16. *Unreleased Express changes* (Content-Disposition without quotes, =res.send= not
    setting =Content-Length= with =Transfer-Encoding=, default error handler logging the
    whole error object). Position: tests do not assert exact =Content-Disposition= bytes.
17. *ws =closeTimeout= interaction with the wrapper deadline.* Two timers race
    (ws 30 s vs wrapper 2 s → =terminate()=). Position: the wrapper's =terminate()= wins;
    verify no double ='close'= event in Phase 3 tests (ws guards this in =close()=, SRC).
    *VERIFIED (=ws-test/close-terminates-an-unresponsive-client-once=): a paused peer is
    terminated at the wrapper's deadline (150 ms in the test), =stop!= reports
    ={:closed 2 :terminated 1}=, exactly one close event per connection.*
18. *Node =shouldUpgradeCallback= (22.21+).* Could replace the manual 404 for non-ws
    paths. Position: not used (portability to Node 18/20); the manual raw response stays.
19. *Body-parser =verify= / =reviver= / =type= function options* need JS functions with
    Node objects (=req=). Position: passthrough (=option-passthrough-keys=), documented as
    "you receive Node objects"; =:type= as string/vector is the supported form.
20. *=@types/*= drift.* The =.d.ts= census is from DefinitelyTyped, not Express; where it
    disagreed with the installed source nothing was found, but new options (e.g.
    body-parser =depth=, cookie =partitioned=) show up in typings first. Position: the
    installed *source* wins in every docstring citation.

** 11.2 Single binding namespace (=express-cljs.core=)
*Corrected in Phase 4 (section 13): two binding namespaces — =core= for Express / Node
(="express"=, ="http"=, ="crypto"=, ="stream"=) and =express-cljs.ws= for the ="ws"=

The only file that =require=s ="express"=, ="ws"=, ="http"=, ="crypto"=, ="stream"=; house

** 11.3 The req map (fields enumerated)
={:method :url :original-url :base-url :path :params :query :body :headers :cookies
:signed-cookies :ip :ips :protocol :secure? :host :hostname :subdomains :xhr?
:http-version :remote-address :remote-port :accepts :accepts-encodings :accepts-charsets

** 11.4 The response map
={:status 200 :headers {} :body v :type kw|str :json bool :cookies [..] :clear-cookies [..]
:vary [..] :links {..} :redirect s|{:url :status} :send-file {:path :root ..} :download {..}
:attachment s :format {..} :end true}=; exactly one of =:body= / =:redirect= / =:send-file=
/ =:download= / =:format= / =:end=; =nil= from a handler means "not mine" (=next()=), a

=:end=). A thrown =util/http-error= is the error path. Unknown keys / two body keys / a

** 11.5 core.async design (Phase 3)
- =ws/connections wss= → channel of ={:event :open :conn c}= / ={:event :close :conn c :code :reason}=
  (buffer 64, =put-or-cancel!= from the leveldb precedent; closing the channel
  unsubscribes).
- =ws/messages conn= → one channel per connection, ={:type :text|:binary :data ..}=, closed
  when the socket closes; full buffer → =pause()=.
- =core/events server= → ={:event :error|:listening|:close|:request-error ...}=.
- Sends are promises (=send!= resolves on the write callback), never channels.
** 11.6 Test strategy
Ephemeral loopback port per test (=listen! {:port 0}=), Node =fetch= (global on 22) and
the =ws= client (already installed) inside =test_util= only; every test closes the server
with =close!= and asserts the port is released; the app ='env'= is =test= (Express's
logger stays quiet); a final "process exits" assertion runs in the Phase 5 smoke, not in
the unit suite.
